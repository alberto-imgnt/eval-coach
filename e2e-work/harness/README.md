# Stand-in end-to-end harness

Stand-in only: the CLI is `fake_cli.py`, never a real CLI. Lesson stages refuse to run unless `E2E_PROFILE=standin`.

## Run everything

```
node e2e-work\harness\run-all.js --fresh                      # Script track
node e2e-work\harness\run-all.js --fresh --track promptfoo    # promptfoo track
node e2e-work\harness\run-all.js --fresh --both               # Script pass, then promptfoo pass
```

`--fresh` builds a private archive of the current `app\` (`e2e-work\eval-coach-e2e.pyz`, so a rebuild of `dist\` mid-run cannot change
what is tested), deletes the pass's stand-in home, project and state, then runs each stage in its own process. Other options:
`--from <stage>`, `--only <stage>`, `--track script|promptfoo`, `--both`. Write its output to a file (`> out.txt 2>&1`) rather than a pipe: the app server a stage starts is
detached, and on Windows a detached child can hold a pipe open.

The promptfoo pass has its own home, project, state and logs (`standin-home-pf`, `standin-project-pf`, `harness-state-standin-pf.json`, `logs-standin-pf`; set `E2E_TRACK=promptfoo` when running `run.js` by hand). It runs the REAL pinned promptfoo 0.125.1: before the pass `run-all.js` links the spike's private Node (`spikes\phase0-preflight\runtime\node-v26.13.0-win-x64`) and npm cache (`spikes\phase0-preflight\npm-cache`) into the stand-in home as `runtime\node` and `npm-cache` (junctions, never copies), so preflight finds and runs them and the app's eval runs offline. The junctions are removed on their own (never recursively) before the home is deleted and again after the pass, so the spike's files are never touched. Only the CLI is a stand-in; the config the stand-in CLI writes is a real `promptfooconfig.yaml` with the `echo` provider (`standin-promptfooconfig.yaml` is its reference text).

By hand: set `E2E_PROFILE=standin` (and `E2E_PYZ` to use another archive, `E2E_TRACK=promptfoo` for the promptfoo track), then `node e2e-work\harness\run.js <stage>` in this order (the promptfoo track adds `fixtures-config` after `fixtures`):

## Real-tool check of the paste flow

`node e2e-work\harness\real-paste.js <claude|copilot|devin>` runs the one real session per tool that the `step-flow` change needs (user-approved 2026-11-19; each real-CLI run needs the user's approval, see AGENTS.md). It is not part of `run-all.js`. It starts the real app on a throwaway home and project under `e2e-work\real-paste\<tool>\`, saves a cold prompt in the page (the AI window opens by itself on Sonnet), presses the page's own Copy button, pastes the copied text into the real terminal with a paste event and Enter, and answers only what the approval checker in `lib.js` allows (one single-use Yes for the folder-trust question and for creating `output.txt`; never "don't ask again", never auto mode). It decides only from files and the step's state: it checks that the page has no Send or Check button, that nothing was typed before the paste, that the folder held only `prompt.md`, that the copied text equals `prompt.md`, that `output.txt` was filed, that the step finished by itself with the model recorded by the app, and that the page stayed on the finished step with Continue offered. Claude Code starts in auto mode by default now, so the script is run with `ALLOW_CLI_DEFAULT_AUTO_MODE=1` for that tool only. Result on 2026-11-19: 17 checks passed for each of the three tools.

`node e2e-work\harness\real-paste-part3.js <claude|copilot|devin>` is the Part 3 version for the `part-3-ai-flow` change (user-approved 2026-11-19: one `generate` run 1 and one `build` start per tool). It uses `e2e-work\real-paste3\<tool>\`, marks the lessons before the steps done in the throwaway project's progress file, opens `generate` (the AI window must open by itself, with no Send or Start again on the page), presses Copy, pastes the line with a paste event and Enter, and lets the harness answer only the allowed single-use Yes prompts until the run is filed as `runs\run-1.txt` and the window closes. Runs 2 to 5 are copied from the Northwind samples so `generate` passes (its window must close with the pass); then `build` opens and its window must start by itself in the project folder with nothing typed (nothing is pasted there). Result on 2026-11-19: Claude Code, Devin CLI and GitHub Copilot CLI each passed 23 checks. Copilot CLI's folder-trust dialog names no folder, so the first two Copilot attempts stopped there (the checker required a folder under `e2e-work`). With the user's approval the checker in `lib.js` now accepts a trust dialog that names no folder only when nothing on screen names another folder and the harness itself started that AI in a folder under `e2e-work`; `classifier-check.js` has a case for each side of that rule.

`fake_cli.py` also writes `e2e-work\fake-cli-events.jsonl` (launches, arguments, typed lines, approvals). The harness reads it to prove the
app added no flags, typed nothing but the activity's line, and answered no prompt. It also prints a decoy result on screen only.

For the `baseline` stage the stand-in answers the run + log line by running the project's own `check.py` on `runs/run-1.txt` to `run-5.txt` and
writing `iteration-log.md` in the exact format of the build skill's Mode 3 (the stand-in computes the counts, a real CLI would too). With
`e2e-work\fake-cli-mode.txt` set to `wrong-count` it logs the first criterion that has a pass one pass too low, so the gate's failure message is
exercised. On the promptfoo track the stand-in also builds the config (`standin-promptfooconfig.yaml`: `echo` provider, `javascript` checks, the same C1 to C6 rules as the reference checker), adds the two fixture tests on the `fixtures-config` line, explains it on the readback line, tightens the C3 assertion on the fix line, and writes the log from the independent reference checks (`pf-independent-check.py`, generated by the harness, never read by the app). The stand-in session budget is 27 (it was 18, 20, 22, 23, then 26; the course restructure removed the rules demo and two of the four lesson practice runs, leaving `build-try` and `fix-try`). The baseline stage uses 2 sessions, the promptfoo track's `fixtures-config` stage 1 and its `live` stage 1, and the `part1` stage 4 (the cold run and one rewrite run for each of the three label sets), which makes 27 on that pass. The real-CLI session budget has been lifted; each real run needs the user's approval (see AGENTS.md). Part 1 needs two real sessions (the cold run and the rewrite run) and the user's approval.

`classifier-check.js` is unchanged: `node e2e-work\harness\classifier-check.js`.
