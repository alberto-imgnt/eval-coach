# eval-coach: build specification

Standalone app for the **"Evaluated Systems (Stage 3)" series**. It teaches the series Part by Part, asynchronously: Part 1 (structured prompting), Part 2 (defining evaluation criteria) and Part 3 (running evals and baseline) are built, Parts 4 and 5 are "Coming soon" and Part 6 is a live meeting (see "Series map" and "Parts"). There is no presenter and there are no handouts: every instruction lives in the app. The app is a **wrapper around the participant's own AI CLI**. Mac is deferred, so keep OS-specific code in `conpty.py` and the setup scripts.

How this document is organised: the rules, layout, storage, HTTP contract, setup and the Series map apply to every Part. The sections "Steps in this slice", "Promptfoo track", "Content guidance", "Troubleshooting coverage" and "Optional live mode" are **Part 3's** step contract. "Part 1" and "Part 2" are those Parts' own contracts. "Parts" explains how the engine holds them side by side. Where an OpenSpec spec exists for an area it wins over this file.

Source material for the content is kept outside the repository (read-only, never modify; the maintainer keeps its location in a local note, `docs/local/SOURCE-MATERIALS.md`). Tests that compare bundled files with their source read the folder from the environment variable `EVAL_COACH_SOURCE_MATERIALS` and skip when it is not set. It holds the Part session plans, the three bundled agent skills (copied unchanged into `kit/skills/`), the Northwind starter files and reference results.

## Non-negotiable rules
- Python standard library only at runtime. Target Python 3.9+; use `from __future__ import annotations`. No pip packages.
- The app sets **no permission flags** on the CLI and never answers CLI prompts. The participant answers them in the embedded terminal.
- The CLI is whatever command the participant enters (it may include arguments, for example `claude --model sonnet`). There is no allowlist and no CLI-specific logic in the app, except the data in `cli-recipes.json`. That data includes each supported tool's `models` entry: the app passes the Sonnet or Haiku choice as a launch option (see "Model choice"). A command with no `models` data starts with no model option. The app does not hold API keys or call any model itself.
- Terminal output is displayed only. The app never parses it to make decisions. It decides by reading files and by running the checker itself. One scoped exception: for a tool that needs an exact model ID, the app may read the tool's own `/model` list in memory to get that ID, and the text shown before it only to avoid typing into a question; never for a result (see "Model choice").
- "New chat" means a new CLI process. Only one CLI process runs at a time.
- Nothing is sent anywhere except by the participant's CLI. No telemetry. The app's own network use is limited to consented preflight downloads from python.org, nodejs.org and the npm registry; it fetches nothing else and sends nothing.
- Plain language for non-technical readers. Never mention a facilitator, presenter, room, breakout, chat waterfall, handout, neighbor or clock. "Script track" and "promptfoo track" replace Room A and Room B. One exception (authorized 2026-11-15): Part 6 is a live troubleshooting meeting, so `baseline-why` "Your own work" says, as information only, that it happens live and that task ideas can be brought to office hours or the AIR discussion. No other text points people to anyone. The only other mention of the live meeting is the Series map's Part 6 row (authorized 2026-11-15), which says, as information only, that Part 6 is a live meeting and what it is about; it never names office hours, the AIR discussion, or any person, place, contact detail, link or schedule.
- Copilot Chat in Teams is not an approved tool and must never be suggested.
- The Northwind weekly update is a learning example and is never a submission option. Participants read it as the "Practice task" (the other starter is "My own task"); the client name stays inside the example's own text, and ids, folders and kit files keep "northwind". Participants read "your AI" and "AI window" where code and these docs say "CLI" (vendor names such as GitHub Copilot CLI and Devin CLI stay). OpenSpec change `content-clarity` (its `participant-vocabulary` spec wins over this paragraph); `tests/test_participant_vocabulary.py` enforces it.

## Storage
- `home` is `%USERPROFILE%\.eval-coach` (override with `--home`).
- Browser `localStorage` holds three display choices only: `eval-coach-theme` (`light`, the default, or `dark`), `eval-coach-nav` (`expanded` or `collapsed` sidebar) and `eval-coach-text-size` (a percentage, 100 by default; 80 to 150 on a desktop, 90 to 130 on a phone). They are never sent to the server and hold no progress or answers. See [DESIGN.md](DESIGN.md).
- `<home>\blind\`: cleared before each run; holds only `prompt.md`.
- `<home>\fixtures-work\`: cleared before the fixtures step; holds only `test-cases.md`, `prompt-v0.md`, `skills/make-eval-fixtures/SKILL.md`.
- `<home>\key-work\`: cleared before the key step; holds only `test-cases.md`, `prompt-v0.md`, `skills/make-eval-fixtures/SKILL.md`, `fixtures/fixture-bad.txt`, `fixtures/fixture-polished-but-wrong.txt`.
- `<home>\sealed\<sha256 of project path, first 16 hex>\answer-key.md`: outside the project on purpose. Written only by the key step, which comes after predictions are locked.
- `<project>\.learning\progress.json`: resumable state, written atomically. It must never contain answer keys or fixture text, and it never holds a course answer (it records which option ids, orders and texts the participant chose, never what was correct). Part 3's step progress stays at the top (`done`, `steps`, `track`); the step progress of every other Part is saved under `parts.<part-id>` (`{"done":[step],"steps":{<id>:record}}`), created the first time that Part saves something and `{}` until then. Part 1's records (`parts.part-1`) hold only the participant's own marks and short texts: `cold` and `rewrite` keep `model_name` (written by the app at each AI start, never typed), `prompt_hash` (of the saved prompt the AI started with, and of a later save while it runs), `auto_started` (true once the step's AI window has been started by the app or the participant, so a save never starts it a second time) and `last_check` (`rewrite` also `framework`), `score` keeps `answers` (yes or no per requirement), `gap` and `in_prompt`, `rescore` keeps `answers` and `reflections`, `own` keeps `labels`. Part 2's records (`parts.part-2`) hold only the participant's own ticks and choices: `draft` keeps `checks` (`traces`, `distinct`), `thresholds` keeps `checks` (`script_test`), `reference` keeps `choices` (reference criterion id to one of `had`, `missed`, `different`, `vague`), and `test-file` keeps nothing but `last_check`; no record holds a worksheet text, a file text or a reference criterion. Prompts, outputs and the own-work texts are files, never progress. Lesson progress of every Part is in the one `lessons` block, which also holds `skipped_parts` (the ids of Parts the participant skipped, `[]` by default; also kept in `pending-lessons.json` before a project exists; cleared by both resets). Demo access is never stored; the hash that checks it is `app/eval_coach/demo_hash.json` inside the app, never in the home folder. A file with no `parts` key loads unchanged and is not rewritten until something changes. See "Parts".
- `<project>\part-1\`: Part 1's own work, written only by the app: `prompt-cold.md` and `prompt-framework.md` (the participant's words, replaced only by Save), `output-cold.txt` and `output-framework.txt` (the AI's `output.txt`, filed by the app), `own-before.md` and `own-after.md` (the `own` step, replaced only by Save). `<home>\part1\cold\` and `<home>\part1\rewrite\`: scratch folders cleared before each AI start (the first save of a prompt, or "Open a new AI chat"); they hold only `prompt.md` (the participant's words, a divider line from content, `kit/part1/rough-notes.txt` and the closing line: the same text the page offers to copy; rewritten by a prompt save while the AI runs) and what the AI writes.
- `<project>\part-2\`: Part 2's own work, written only by the app: `worksheet.json` (`{"rows":[{"requirement","criterion","type","threshold"}]}`, replaced only by Save in `draft` and `thresholds`) and `test-cases.md` (the participant's file, replaced only by Save or a confirmed Build in `test-file`, or by Save in `reference`). Part 2 starts no CLI, so it has no `<home>` scratch folder and no output files.
- `<project>\.learning\hook\run-1.txt` to `run-3.txt`: the three grades of the `hook` lesson. `<project>\.learning\results\`: saved checker runs, including `demo-1.json` and `demo-2.json` from the `rules` demo and `baseline.json` (the baseline step's own run: `{"track","result":RunResult,"summary":BaselineSummary}`, see `baseline.data`). On the promptfoo track `<project>\results.json` is written by the eval (the app deletes it before each run) and read by the summarizer and for reasons; `<project>\promptfooconfig.yaml` is written by the participant's CLI. `progress.json` `track` is `"script"` or `"promptfoo"` once a step is done. `<project>\iteration-log.md` is written by the participant's CLI in the `baseline` step; the app only reads it and never changes it.
- `<home>\hook\`: cleared before each hook run; holds only `update.txt` and `requirements.md`. `<home>\demo\`: cleared before the anatomy demo; holds only `test-cases.md`, `output.txt` and `skills\build-eval-script\SKILL.md`, plus whatever the CLI writes (`check.py`).
- `<home>\pending-lessons.json`: course progress made before a project exists (the mission). It has the same shape as the `lessons` block below and is merged into `progress.json` when the project is set up.
- `<home>\preflight.json`: preflight results, track choice, the AI command, `setup_skipped` (true once the participant skipped setup; a configuration reset forgets it) and `model_preference` (`"sonnet"` or `"haiku"`, default `"sonnet"`; a configuration reset returns it to Sonnet, a lesson progress reset keeps it). Written atomically. A `signin` item and `signed_in_command` / `launched_command` from older files are ignored, not migrated.
- `<home>\model-cache.json`: exact model IDs found by the hidden `/model` read, per tool: `{"<program>":{"program":"<path>|<size>|<mtime>","ids":{"sonnet":str,"haiku":str}}}`. Only IDs and the program marker (read from the file system); never screen text, an account name or an email. Moved by a configuration reset, kept by a progress reset. `<home>\cli-models\` is the empty scratch folder that read runs in; it is left in place.
- `<home>\runtime\node`, `<home>\npm-cache`, `<home>\promptfoo`: private Node.js, npm cache and promptfoo config, created only after consent.
- `<home>\cli-test\`, `<home>\cli-install\`: cleared and used only for the working test and install recipes. An old `<home>\cli-signin\` is no longer created and is left in place if present.
- `<home>\cli-recipes.json` (optional): replaces the bundled recipes without a rebuild.
- Default project path: `%USERPROFILE%\eval-project`. A new project inside OneDrive is refused by item 8; an existing one keeps its progress but fails item 8 until moved.
- `<home>\reset-backup\` (one slot): everything the last reset or "Start this step again" moved out, under `project\` (project folder files, same relative names) and `app\` (files and folders from `<home>`). It is built in `<home>\reset-backup.new\` and replaces the previous backup only when complete (a restart that moves nothing leaves it alone). It never holds an answer key. It is a plain folder; the app does not read it or restore from it.
- Never overwrite an existing participant file when creating a project. If `.learning\progress.json` exists, resume.

## Steps in this slice (both tracks)
*Part 3's steps. Part 1's and Part 2's steps are in "Part 1" and "Part 2"; the routes below also serve them through their step kinds (see "Parts").*
Order on the Script track: `generate`, `build`, `fixtures`, `readback`, `predict`, `key`, `run`, `fix`, `baseline`. The promptfoo track has the same steps plus one extra step, `fixtures-config`, right after `fixtures`: `generate`, `build`, `fixtures`, `fixtures-config`, `readback`, `predict`, `key`, `run`, `fix`, `baseline`. `state.STEP_IDS` and `state.COURSE` stay the Script lists; `state.step_ids(track)` and `state.course_items(track)` give the list for a track. A step unlocks when the previous one is done and the lesson immediately before it, if the engine has a course, is done or skipped (see "Course and lessons"). Done steps stay viewable. Every step stays locked, and step routes are refused with `preflight_incomplete`, until every applicable preflight item passes (see `docs/SETUP.md`). A step that order has not opened (an earlier lesson or step is not done, or an earlier Part is not Done or Skipped) is refused with `step_locked` and one plain message, `content/lesson-ui.json` `ui.locked_tip` ("Opens when the previous ones are done"); see "Course locking".

**Track.** Preflight item 1 stores `"script"` or `"promptfoo"` (`Preflight.track`). The track is fixed for a project once any step is done: the first done step writes `progress.json` `track`, the engine then uses that track whatever preflight says, and `POST /api/preflight/track` with a different value is refused with `track_locked` (the preflight screen disables the radios and says why in plain words, `state.preflight.track_locked` and `track_locked_note`). Before any step is done the track can change and the step list follows. A `progress.json` with no `track` key (older files) is read as the Script track unless the extra step is in `done`. The Script track's step list, progress files and tests are unchanged; the extra step's record is created only on the promptfoo track. Text for steps that differ by track lives in `content/steps.json` under `steps.<id>.tracks.promptfoo` and is deep-merged over the shared text (goal, why, instructions, troubleshooting, `cli.line`, `ui`, gate messages); steps with identical text (generate, predict) stay shared. The lessons are shared by both tracks (the `rules` lesson's demo still builds a Python `check.py`). The table and the gates below are the Script track's; the promptfoo track's differences are listed in "Promptfoo track".
| Step | CLI starts in | Line the participant pastes (exact) |
|---|---|---|
| generate (5 runs) | `<home>\blind` | `Read prompt.md, follow it, and save only your answer to output.txt. Do nothing else.` |
| build | project | `Read skills/build-eval-script/SKILL.md and follow it in build mode on test-cases.md.` |
| fixtures | `<home>\fixtures-work` | `Read skills/make-eval-fixtures/SKILL.md and follow it for test-cases.md and prompt-v0.md, with one change: write only the two fixture files. Do not write the answer key, and do not say what is wrong with either fixture.` |
| readback | project | `Read skills/build-eval-script/SKILL.md and follow it in explain mode on test-cases.md and check.py.` |
| predict | none | none |
| key | `<home>\key-work` | `Read skills/make-eval-fixtures/SKILL.md. The two fixture files are already in fixtures/. Do not change them. Follow only the Answer key section, using test-cases.md, and write fixtures/answer-key.md. Do nothing else.` |
| run | none | none |
| fix | project | `I changed test-cases.md. Update check.py to match, changing only the functions whose threshold changed. Then run the two fixtures again.` |
| baseline | project | `Read skills/build-eval-script/SKILL.md and follow it in run + log mode. The runs are runs/run-1.txt to runs/run-5.txt. The prompt file is prompt-v0.md. The model was <model>.` where `<model>` is the models the app recorded for the Part 3 runs (`models_used` of the generate step, joined with " and "), forced to one line before typing (every run of whitespace, line break or control character becomes a single space, then trimmed). The line is never held back for a missing model: every AI start records one. |

Typing: the app types nothing into the AI for any step in this table. Each of the nine AI steps (`generate`, `build`, `fixtures`, `fixtures-config`, `readback`, `key`, `fix`, `baseline` and the optional `live`) uses the paste flow: the page shows the line, the participant copies it and pastes it into the AI window (OpenSpec change `part-3-ai-flow`; its `part-3-paste-flow` and `ai-window-paste-flow` specs win over this section).

**Part 3 paste flow.** `content/steps.json` has `cli_mode: "paste"` on those nine steps and a top-level `paste_ui` block (the shared note, Copy words, "Open a new AI chat" and its confirm) that the loader (`lessons.load_step_content`) merges under each paste step's own `ui`. `cli` is `{line, folder_label, mode:"paste", started, sent:false, blocked, can_auto_start, has_result, paste_ready}` (`live` also has `start_blocked`). `line` is the text to paste (the table's line, with `{model}` and `{cli}` filled in); `paste_ready` is false while a part of it is unknown (`live` before the warning is ticked and an AI chosen, or a `<model>` placeholder). `blocked` holds the reason an automatic start failed. The AI window head shows the line (`#cli-line`), Copy (`#copy-paste`, status line `#copy-status`), "Open a new AI chat" (`#cli-start`) and Stop; there is no Send and no Start again, and `/api/step/send` is refused (`not_supported`).
- **Automatic start.** When the page shows an active paste step whose `cli.can_auto_start` is true it calls `POST /api/step/auto-start` once per visit. `engine._auto_start_ok(step)` (also the source of `can_auto_start`) requires: paste mode, not `live`, the step active (`_require_active`: not done, not locked, setup passed), no AI process running, `auto_started` false in the step's record, no earlier failed start (`_cli_blocked`), and a "nothing to lose" check per folder: `generate` needs a run still to do and `<home>\blind` holding nothing but `prompt.md`; `fixtures` needs no fixture text in `<home>\fixtures-work\fixtures` or `<project>\fixtures`; `key` needs no text in `key-work\fixtures\answer-key.md` and no sealed key (file presence only: the sealed key is never opened); the project-folder steps need nothing more. It then runs `_launch_step`, the one routine behind both this and `step_start`: clear and prepare the step's folder, start the AI on the chosen model, record the model, note `live`'s start hashes, start the `generate` watcher. Every start of a paste step (automatic or by the button) sets `auto_started`, so Stop then revisit never starts again. A failed automatic start never raises: it sets `cli.blocked`, leaves `auto_started` false and leaves "Open a new AI chat" as the retry. `generate` runs 2 to 5 and `live` start only by "Open a new AI chat" (`step_start`; run label "run n of 5").
- **Open a new AI chat** is `POST /api/step/start`. The page asks first (confirm dialog) when a window is running or `cli.has_result` is true (a result in the step's scratch folder that a new start would clear: for `generate` anything in `blind` but `prompt.md` and an `output.txt` already saved as a run; for `fixtures` fixture text in the work folder; for `key` text in the key work folder; false for project-folder steps). The server does not enforce the confirm.
- **A finished step closes its window.** A passing "Check my work" stops the step's own AI window, so the next step can open its own by itself.
- **Unchanged:** every gate, nudge and "Check my work", the model recording at every start, the sealed key handling, the folders' lifecycles. `progress.json` step records of the nine steps gain `auto_started` (default false; a record without it loads with the default).

Step behavior and gates:
- **generate**: the app starts the participant's CLI on the model chosen with the Sonnet / Haiku toggle (see "Model choice") and records the model; the participant types no model name. Start clears the blind folder and copies `prompt-v0.md` to `prompt.md`. A watcher polls for `output.txt`; once it is non-empty and unchanged across two 1-second polls, copy it to `runs/run-n.txt`, stop the CLI, advance `current_run`, push an SSE `state` event. Done when 5 non-empty run files exist and a model was recorded (`model_name` is non-empty).
- **build**: gate: `check.py` exists; the scan passes; participant ticks the two handback items (read NOT CHECKED, read Interpretation choices); the first look was run. First look: app runs `check.py runs/run-1.txt`.
- **fixtures**: gate: `fixture-bad.txt` and `fixture-polished-but-wrong.txt` are non-empty in `<home>\fixtures-work\fixtures\`, and `<project>\fixtures\answer-key.md` does not exist. With the Northwind starter, `POST /api/step/use-example-fixtures` can put the example's two fixtures in that folder when the CLI could not (see "Troubleshooting coverage"); the gate is the same. On pass, copy the two outputs to `<project>\fixtures\`. If the CLI wrote `answer-key.md` under `fixtures-work` anyway, delete it when the gate passes and add this non-blocking nudge: `Your CLI wrote an answer key anyway. The app deleted it, and a new one will be written after you lock your predictions. If you saw what it said, predict as honestly as you can.` After a pass, no answer key exists anywhere: not in `fixtures-work`, not in `key-work`, not in sealed storage. `<project>\fixtures\answer-key.md` must never exist. Writing the key after predictions lock is the safeguard, because a CLI's approval prompt can print the whole file on screen before the participant predicts.
- **readback**: gate: at least one `examples/c*-pass.txt` exists and every criterion has a Yes or No.
- **predict**: grid rows come from `test-cases.md`; if parsing finds no criteria, `manual_rows` is true and the participant adds rows. Gate: every cell (P, F or NC, for both fixtures) and the three answers filled. Submitting with `lock: true` locks it permanently.
- **key**: locked until predict is done, which requires locked predictions; `/api/step/start`, `/send` and `/check` are rejected before that, as for any locked step. Start clears `<home>\key-work\` and writes exactly: `test-cases.md` (the project's current copy), `prompt-v0.md`, `skills/make-eval-fixtures/SKILL.md`, `fixtures/fixture-bad.txt`, `fixtures/fixture-polished-but-wrong.txt` (from the project), and nothing else, in particular not `check.py` or `runs/`. Gate: `<home>\key-work\fixtures\answer-key.md` is non-empty; both fixtures in `key-work` still hash the same as the project's copies; `<project>\fixtures\answer-key.md` does not exist. On pass, **move** the key to sealed storage.
- **run**: requires locked predictions. App runs `check.py fixtures/fixture-bad.txt fixtures/fixture-polished-but-wrong.txt`. The answer key is returned only after predictions are locked and this run succeeded on that state; key text must never appear in any API response before that. Gate: every surprise classified (`vague`, `reads_differently`, `predicted_wrong`).
- **fix**: participant edits `test-cases.md` in the app. Gate: `test-cases.md` hash differs from its hash at the start of the step; `check.py` changed after that edit; the scan passes; app reran both fixtures; the bad fixture fails more than half its checked criteria; the polished fixture fails at least one criterion or the participant wrote why it should pass. If `check.py` changed while `test-cases.md` did not, add a nudge: fix the spec, not the checker. The step may be skipped only if there were no surprises and the polished fixture already failed at least one criterion.
- **baseline**: locked until `fix` is done or skipped, and until the `baseline-why` lesson is done or skipped. The participant's CLI starts in the project folder and writes `iteration-log.md` in the format of the build skill's run + log mode (Mode 3). The participant also presses **Run my checker on the five runs**: the app runs one `check.py runs/run-1.txt ... runs/run-5.txt` through `runner.run_checker` (exit 0 and 1 are normal), through the track-agnostic `baseline.run_checks(project, track, env)` which returns a RunResult (a track adds its own runner to `baseline.RUNNERS`; only `script` exists, and any other track uses it for now). The run is refused unless the step is active, `check.py` exists and passes the scan, and all five run files are non-empty. Per-criterion results are saved in `results\baseline.json`; the file hashes (check.py, and one hash over the five runs) at the time of the run are saved in progress. A criterion is **not checked** when every run says NOT CHECKED; otherwise `passes` counts PASS, `checked_runs` counts PASS and FAIL, and `failing_runs` lists the FAIL runs. `overall` is passes over checked results, so NOT CHECKED criteria are left out. Gate (it only reads `iteration-log.md`; the app never edits it, `check.py` or a run): (a) `iteration-log.md` exists and has exactly one `Iteration 0` entry (any title; the skill writes `Iteration 0: baseline`); (b) the app's run was done on the current runs, and `check.py` and the five runs hash the same as when it ran; (c) for every checked criterion the log's table row has the same pass count and checked count as the app's, and the log's `Overall` equals the app's `passes / total`; (d) the log's `Not checked` line lists exactly the criteria the app saw as NOT CHECKED (a NOT CHECKED criterion must not be given a pass count in its row, and a stated count must match the IDs listed); (e) `Runs` is 5. Any mismatch fails and says so in plain words with both numbers, for example `The log says C2 passed 4 of 5 runs. The app counted 3 of 5.` Empty `Prompt` or `Model` lines only add a nudge. On a pass the CLI is stopped. The iteration-log parser (`parsers.parse_iteration_log`) accepts reasonable variation (extra spaces, `4 / 5`, `80 %`, CRLF, a BOM, bold markers, any heading level) and raises `IterationLogError` for a log with no `Iteration N` entry. The step teaches: the baseline is the starting number for the next iteration (Part 4 compares with it), thresholds were settled before logging, NOT CHECKED means not covered, and the checker is never edited to make a failing output pass.

Resuming older progress: a `progress.json` written before the key step existed has no `key` entry and must load without error. If it has one, nothing changes. Treat `key` as done when the sealed key exists and predict is done, otherwise locked or active by the normal rules; steps after `key` recorded as done without a sealed key go back to not done. A `progress.json` written before the `baseline` step existed has no `baseline` entry and loads with the default one; if `fix` was done, `baseline` is simply the next step, and nothing is marked done that was not. A `progress.json` with no `track` key loads as the Script track and gets no `fixtures-config` entry; one whose `done` list holds `fixtures-config` is read as the promptfoo track. `track` is written when the first step is done and never changes after that.

Scan (`scan.py`): parse `check.py` with `ast`. Fail on imports of network or model libraries (`socket`, `http`, `urllib`, `requests`, `httpx`, `aiohttp`, `ftplib`, `smtplib`, `openai`, `anthropic`, `google.generativeai`, `langchain`, `litellm`, `boto3`, `subprocess`) with a plain message. It is a warning mechanism, not a sandbox.

Runner: `subprocess.run([sys.executable, "check.py", ...], cwd=project, timeout=30, capture_output=True, env = the CLI environment plus PYTHONUTF8=1, PYTHONIOENCODING=utf-8, creationflags=CREATE_NO_WINDOW)`. Exit 0 and 1 are normal; anything else, a timeout or unparseable output is a reported error.

Checker output format to parse:
```
== <file>
C1 PASS  Length: 58 words (limit: under 150)
C3 NOT CHECKED  Tone: needs judgment: ...
-> 4 passed, 1 failed, 1 NOT CHECKED
```
Also accept the older `-> 1/6 criteria passed` summary. Ignore the `== Pass rate per criterion` section.

## HTTP contract
Bind `127.0.0.1`, random port by default. Token: `secrets.token_urlsafe(32)`, compared in constant time. Launch URL: `http://127.0.0.1:<port>/?t=<token>`.
- API requests send header `X-Eval-Token`; the SSE request uses `?t=`. Static files need no token.
- Reject any request whose `Host` is not exactly `127.0.0.1:<port>`, and any request with an `Origin` other than `http://127.0.0.1:<port>`.
- POST bodies are JSON with `Content-Type: application/json`; limit 2 MB.
- No CORS headers. CSP: `default-src 'self'; style-src 'self' 'unsafe-inline'; connect-src 'self'; frame-ancestors 'none'`. Static paths cannot traverse.

Routes. Every POST returns `{"ok":true,"state":State}` (plus `"result"` for the course routes below) or an HTTP 400 with `{"ok":false,"error":{"code":str,"message":str},"state":State}`. The course GET routes return `{"ok":true, ...}` with a named field, or the same 400 error body.

## Optional live mode
*Part 3 only (the promptfoo track's optional `live` step).*
Live mode was built on purpose, with an explicit warning. Live mode is the build skill's Mode 4: promptfoo writes fresh outputs through the participant's own signed-in agent CLI, using the bundled `agent-provider.js` (byte-identical to the Session 3 source) as an `exec:` provider.

| `project_exists` | warning | The project folder already has progress, so nothing will be imported |

**Content heuristic (4.22, blocking).** A criterion is about the content of the answer when its *threshold* requires particular information to be present (named terms, labels, topics, facts, or things copied from the input), and is not about content when it only measures size or shape, only forbids things, or relies on judgment. Applied to the threshold text: (1) count phrases such as "under 150 words" or "at least 3 sentences" are removed; (2) what is left is content if it has a coverage word (all, any, each, every, both, at least N, one of, some) before "appear", "present", "found", "included", "mentioned" or "contains"; or a presence verb (contains, includes, mentions, covers, states, names, cites, quotes, lists, references, says) followed by an object; or a term or label word followed by "appears"; or a quoted term with a presence word and no negation anywhere; (3) otherwise the criterion's own `Type` line (heading layout, or a Type / "Format or content" table column) saying "Content" is trusted, unless the threshold is only a count or contains a vague word. A `Format` label never hides a threshold that requires terms (Northwind's C2 is labelled Format and still counts). It blocks because without one the checker cannot catch a polished but wrong answer; it is deliberately generous so a good file is not turned away on wording.

**Tracing heuristic (4.23, warning).** A criterion is traced when it has Requirement text (a heading `Requirement:` line or table column), or its name shares a key word with the prompt, or its threshold shares a number or at least two key words with the prompt. A key word has four or more letters and is not a generic checking word; words match on their first five letters ("grouped" matches "group"). It only warns because a keyword heuristic can be wrong.

**Vague words (4.24, warning).** clear, good, great, concise, professional, relevant, accurate, helpful, natural, appropriate, easy, nice, engaging, effective, friendly, polite, readable, coherent, useful, informative, well-written, well-structured, high-quality, and their "-ly" forms, matched as whole words in any case. Words inside quotation marks or backticks are terms the participant chose and are never flagged. The first nine are the words in the build skill's NOT CHECKED rule.

The Northwind reference test cases and prompt pass every check with no finding, in LF, CRLF, BOM and BOM+CRLF forms (tested).

New error codes: `import_blocked`.

- **Content.** `lessons.load_bundled` validates each Part's `lessons_file` with the same checker against that Part's lesson and step ids (`validate_course(data, glossary, part)`; the Part's `mission` is the lesson allowed to have no questions) and merges them into one `Course` keyed by lesson id (`Course.missions`, `mission_of(lesson_id)`; placement and step-check ids must be unique too). `lessons.load_step_content` merges every Part's step text into `Engine.content["steps"]` (Part 3's file also holds the shared `messages`); a Part's steps file may carry a `ui` object, deep-merged over `course_text` when that Part is the one `GET /api/state` describes. - **Engine.** `_part_of(id)` finds the Part from a lesson or step id, so every route keeps its shape and takes no Part. `_walk(passed, part)`, `_status`, `_lesson_status`, `_lesson_blocking`, `_mark_done` and `_step` read and write that Part's progress (`_progress_of(part)`; reading never creates a block). ### Course locking
OpenSpec change `course-locking` (its `course-locking`, `part-skip`, `demo-access`, `part-registry` and `series-map` specs win over this section; it reverses the archived `read-ahead-always` for participants). One server-side rule decides what opens; the page only shows it.
- **Item rule.** `Engine._walk(passed, part)` gives each item of a Part's course a status: `done`, `skipped`, `active` (the next item to do) or `locked`. A lesson or step opens, for reading and for doing, only when it is done, skipped or active. A locked lesson is refused by `lesson_view` and every lesson route with `lesson_locked`; a locked step is refused by `get_state(step=...)` and every step route (the step kinds' routes too, in `_kind_call`) with `step_locked`. Both carry the one message `lesson-ui.json` `ui.locked_tip` ("Opens when the previous ones are done"), which is also the tooltip. The refusal reads and writes no participant file and no saved progress, and the `key` step is refused like any locked step, so the sealed answer key is never opened for it (AGENTS.md rule 9). `preflight_incomplete` still comes first for hands-on routes when setup has not passed. Before setup the lesson that is next to do is `active` (its CLI exercises are refused with `preflight_incomplete`), and a step that is next to do opens as its words only.
- **Part rule.** `Engine._part_open(part)` is true when every Part with a lower number is finished (`_part_finished`: every lesson `done` or `skipped` and every step in its `done` list, by saved status only, or the Part is in `lessons.skipped_parts`) or demo access is on. When it is false `_walk` returns every item `locked`, even items done earlier (a participant already ahead is held until the earlier Parts are done or skipped; nothing is deleted). An engine built with no course gates nothing.
- **Part skip.** `POST /api/part/skip {part, confirm:true}` appends the Part id to `lessons.skipped_parts` (`pending-lessons.json` `skipped_parts` before a project exists, merged by `_adopt_pending`) and stops an AI window that belongs to that Part (`Engine._cli_part`). It is allowed for a Part that is open and not finished or skipped, and no file is moved or deleted. A skipped Part counts as finished for the Part rule; `_walk` returns every item `skipped`, `lesson_view` returns a lesson read-only (`status: "skipped"`, `part_skipped: true`, built as a preview so no participant file is read and the shuffle seed is not saved), a step returns its words only (`status: "skipped"`, `part_skipped: true`), and every write route refuses (`lesson_skipped`, `step_skipped`). There is no undo; both resets clear `skipped_parts` with the lessons block. `prune_lessons_block` drops ids of Parts this build does not know, and `skipped_parts` is filled with `[]` on load when absent (the file is not rewritten until something changes).
- **Series state.** `state.series.parts[].state` is `locked`, `not_started`, `in_progress`, `done` or `skipped`; `done` and `total` are null for a locked or skipped Part; `can_skip` is true for `not_started` and `in_progress`; `skip` holds the Part's `teaches` and `matters` words for the confirm. `series.active_part` is the Part in progress, else the first open Part not started, else null (the page expands only that Part after a launch or reload). `related.lessons[].open` tells the page whether to link a related lesson.

### Demo access
OpenSpec change `course-locking` (its `demo-access` spec). A hidden, password-protected way to open every Part for a demo or a test, for the current run only; a deterrent, not a security feature. `app/eval_coach/demo_access.py` holds the check: PBKDF2-HMAC-SHA256, a 16-byte random salt, 200,000 iterations, compared with `hmac.compare_digest`, against the record `{salt, hash, iterations}` in `app/eval_coach/demo_hash.json` (shipped in the archive; made by `python tools\make_demo_hash.py`, which reads the password with `getpass` and never prints or stores it). The password is never in the repository, specs, tests, docs, logs or the shipped app. With no hash file demo access is unavailable (`state.demo.available` false) and the version line in Settings does nothing. `Engine(..., demo_hash=record)` takes a record directly (tests build their own with a throwaway password), and the hidden `--demo-hash-file <path>` launch flag (suppressed from `--help`) loads one for the harness and the interface tests.
- **Routes.** `POST /api/demo/unlock {password}` turns it on (a wrong or empty password is refused with `demo_refused` and one plain message, with no hint), `POST /api/demo/lock` turns it off, and `state.demo` is `{available, on}`. The flag is an attribute of the engine only: it is never written to any file, a reload keeps it (the process lives on), closing the app turns it off, and neither reset changes it.
- **Effect.** It makes `_part_open` true for every Part, so any Part can be started. Inside a Part the order stays strict (no reading ahead, as for any participant). It marks no Part done or skipped, does not change the setup rules or the track and does not open the sealed answer key. Work done while it is on is saved like any other; turning it off locks a Part again by the normal rule and deletes nothing.
- **Interface.** Settings ends with a version line (`state.settings.version`, a button styled as text, `#settings-version`); the fifth selection in a row (by mouse, or Enter or Space) reveals the demo group with a password box (`#demo-password`), "Turn on demo access" and, while it is on, "Turn off demo access". While it is on a notice (`#demo-notice`, `role="status"`, no focus) shows on the Series map, inside every Part and in Settings. Its words are in `content/settings.json` `demo`; nothing else in the app, its words or its help mentions demo access.

The stylesheet's responsive rules select on `data-layout` instead of `@media` widths, so a larger text size switches to the more compact form sooner. At 100% it is identical to the earlier layout. `data-phone` is set on `<html>` on a phone, which turns on 44 pixel touch targets in Settings and the banner.
- **Reset.** Two actions, each behind a confirmation dialog whose default action keeps everything; see `POST /api/reset/progress` and `POST /api/reset/configuration`.  "placement":[Choice+{"lesson":id}],
```
 "lessons":[{"id","title","win","minutes","skippable":bool,"body":markdown,
             "activities":[Activity], "retrieval":[Choice],
             "sources":[{"label","ref"}], "primary_source":{"label","ref","why"},
             "related":{"lessons":[id],"glossary":[term]}}]}
Choice = {"id","prompt","options":[{"id","text","correct":bool,"feedback"}]}
```
`ref` is `kit:<path inside app/eval_coach/kit>` or an `https://` URL. The loader (`lessons.load_bundled`) validates everything at start-up and again in the content tests; if it fails, the app prints the problems and exits with code 1 instead of starting. A lesson is invalid when:
- an id is missing or duplicated, a lesson is missing, or a lesson is not in the course order; `version` is not 1; `mission` is empty;
- a choice (activity, CLI question, placement or retrieval) has fewer than two options, not exactly one correct option, feedback missing on any option, or options whose word counts differ (words are whitespace-separated tokens);
- a lesson has no activity, fewer than two `retrieval` items, a retrieval prompt that repeats an activity prompt, no source, or no primary source;
- a lesson with a `rule_lab`, `cli_compare` or `cli_demo` is `skippable`, or a CLI activity sits outside its lesson (`cli_compare` only in `hook`, `cli_demo` only in `rules`);
- a `step_checks` entry is not a valid choice, names a step outside `STEP_IDS`, or repeats a step;
- there are more than 6 placement questions, or one targets `mission` or an unknown lesson;
- a `ref` is not `kit:` or `https://`, or a `kit:` ref is not a readable bundled file (see the kit viewer);
- a `rule_lab` case's `expected` verdict is not what the rule really gives, a rule kind is not in the fixed list, or a CLI line is not the exact line below;
- `related` names an unknown lesson or glossary term;
- (course content tests, not the loader) a lesson body is over its word cap, an old lesson id or removed activity id is present, or a glossary `lesson`, `related` or `sources` reference does not resolve.

### Activities
| `type` | Answer body | Passes when |
|---|---|---|
| `choice` | `{"option":id}` | the correct option is chosen |
| `order` | `{"order":[item ids]}` | every item is listed once, in the right order |
| `sort` | `{"placements":{item id:bucket id}}` | every item is in its bucket |
| `rule_lab` | `{"cases":{"<sample>\|<rule>":"pass"\|"fail"}}` | every case was predicted correctly |
| `reflection` | `{"text":str}` | the text has at least `min_words` words. Short text is saved but does not pass. Once passed, a reflection stays passed: a shorter rewrite is ignored (the passing text is kept), and only another passing text replaces it |
| `cli_compare` | `{"option":id}` (answers its `question`) | the three run files are saved and the question is right. Answering before then gives `runs_missing` |
| `cli_demo` | `{}` (the app decides) | `check.py` exists in the demo folder, the scan passes, and two app-run checks gave identical, usable verdicts |

`rule_lab` rule kinds are a fixed list in Python: `word_count_under {limit}` (strictly under), `all_present {terms}` and `none_present {terms}` (any case, inside longer words), `all_labels {labels}` (exact case, anywhere). The app never runs participant-supplied code. A malformed answer is `bad_answer`.

### Grading rules
- Correct answers, buckets, expected verdicts and the right order stay on the server until the activity is answered. No response contains them earlier. A wrong choice shows only the chosen option's feedback. A failed order shows only generic feedback and the submitted order. A failed sort or rule lab shows only how many are right.
- Retry is unlimited. Each activity stores `passed`, `attempts`, `first_try`, and `last` (the participant's latest answer). A passed activity is closed (answering again changes nothing), except that a reflection can be replaced.
- The shuffle is `sha256(seed:context:id)`, with a `seed` made once per participant and saved in `progress.json`, so the order is stable across reloads and differs between participants. An `order` activity is never shown already in the right order.
- Learning records: viewing creates none. A passed activity creates `{"type":"activity","lesson","item","source":"lesson","at","first_try"}`, a correct placement `{"type":"placement","source":"placement"}`, and a correct review answer `{"type":"review","source":"review"}`. A wrong answer, a skipped lesson and a completed lesson add nothing.

### Views
```
LessonView = {"id","title","win","minutes","skippable","status","mission","body",
  "activities":[ActivityView], "sources":[{"label","ref"}], "primary_source":{"label","ref","why"},
  "related":{"lessons":[{"id","title"}],"glossary":[term]},
  "can_complete":bool, "can_skip":bool, "placement":[PlacementView]  // placement: mission only
}
ActivityView = {"id","type","passed", ...by type}
  choice:      prompt, options[{id,text}], result: null | {passed, chosen, feedback, explanations?[{id,correct,feedback}]}   // explanations only once passed
  order:       prompt, items[{id,text}] shuffled, result: null | {passed, submitted[], feedback}
  sort:        prompt, buckets[{id,label}], items[{id,text}], result: null | {passed, placements, right, total, feedback?[{item,feedback}]}
  rule_lab:    prompt, samples[{id,label,text}], rules[{id,label}], cases[{id,key,sample,rule}], result: null | {passed, predictions, right, total, details?[{key,verdict,reason}]}
  reflection:  prompt, min_words, result: null | {passed, text, words}
  cli_compare: runs, files, cli{line,folder_label,started,sent}, outputs[{n,done,text}] (plain text, never HTML), all_saved, question{prompt,options,result}
  cli_demo:    files, cli{...}, checker_exists, scan[{message}], runs[RunResult], identical: bool|null
PlacementView = {"id","prompt","lesson","lesson_title","options":[{id,text}],
  "result": null | {"passed","chosen","feedback","offer_skip":bool,"decision":null|"accepted"|"declined"}}
ReviewItem = {"item":"<lesson>:<retrieval id>","lesson","lesson_title","prompt","options":[{id,text}]}
```
`can_complete` is true when the lesson is active and every exercise is finished. Only exercises hold Continue back: a `cli_demo` must pass, and a `cli_compare` or `cli_practice` must have its output saved. Every question, order, sort, rule lab and reflection is a learning check that never blocks; a pass still creates a learning record. `can_skip` is true when the lesson is active, `skippable`, and its placement question was answered correctly.

### Step questions
`content/lessons.json` has a top-level `step_checks` list (optional): `[{"id","step","prompt","options":[...]}]` in the `Choice` shape, at most one per step in `STEP_IDS`, validated like any choice (one correct option, feedback on each, equal word counts). The step page shows the question under the gate result once the step is `done`, with the heading `step_check_heading` and note `step_check_note` from `content/lesson-ui.json`. It is graded by `POST /api/step/question`, never gates a step or the course, and is stored in `progress.json` under `lessons.step_checks.<step>` as `{"passed","attempts","first_try","last"}`. The order of the options is shuffled with the participant's seed, as for lessons.

### CLI activities
Both use the terminal, Start and Send pattern (the lessons keep it; Part 3's steps now paste, see "Part 3 paste flow"), and decide only from files. The line is typed exactly, with the 400 ms pause before Enter. Each start stops any running CLI first. In the seven-lesson course the CLI activities are `hook-compare` (`cli_compare`) and the two practice runs `build-try` (lesson `rules`) and `fix-try` (lesson `surprise`) (`cli_practice`, see `docs/RUNNING-EVALS-COURSE.md`).
- **`hook-compare` (lesson `hook`, 3 runs).** Folder `<home>\hook\`, cleared before each run, holding only `update.txt` (the Northwind polished-but-wrong example) and `requirements.md` (`kit/lessons/hook/requirements.md`). Line: `Read update.txt and requirements.md. Score the update from 1 to 10 against the requirements, say pass or fail, and give one sentence of reasoning. Save only that to output.txt. Do nothing else.` Capture works as in `generate` (non-empty and unchanged across two polls), copies to `<project>\.learning\hook\run-n.txt`, and stops the CLI. A fourth start is `runs_complete`.
- **`cli_demo` (supported; no lesson uses it since the restructure, the former `rules-demo` was removed; where one is used it sits in lesson `rules`).** Folder `<home>\demo\`, cleared at start, holding the activity's `files`. The answer route scans `check.py` (`scan_failed` on network or model imports), checks that every `run_args` file exists (`missing_file`), runs `check.py output.txt` twice with the runner, saves both results, and passes only when both are usable and give identical verdicts. A finished demo cannot be restarted (`activity_done`).

### Placement
Shown inside the `mission` lesson, at most 6 questions. A correct answer makes `offer_skip` true for that question's skippable lesson; the participant accepts (`accept_skip: true`, the lesson becomes `skipped`) or declines (the lesson stays; `lesson/skip` still works when it comes up). The decision is final: a second `accept_skip` call, in either direction, is refused with `placement_decided` and nothing changes. A wrong answer changes nothing and cannot be retried (`placement_answered`). Placement closes when the mission is finished (`placement_closed`). Practice steps and non-skippable lessons are never skipped: placement questions may target only skippable lessons. Skipped lessons schedule no reviews.

### Review
- Completing a lesson schedules each `retrieval` item, due 1 day after completion (`review.items["<lesson>:<id>"] = {lesson,item,stage,due,retired}`, times in seconds; scheduling never resets an item).
- A correct answer moves the item to 3 days, then 7 days (counted from the moment of the answer), then retires it after the third correct answer. A wrong answer sets it back to stage 0, due in 1 day.
- A sitting has at most 5 items, chosen oldest-due first and spread across lessons, and ordered so consecutive items come from different lessons when possible. The sitting is fixed once chosen: `GET /api/review` returns it until it is answered, and the rest wait for the next time the app opens. Nothing is shown before it is due. The clock is injected (`Engine(clock=...)`, default `time.time`) so tests control it.
- `postpone` hides the review for this run of the app only; the schedule is unchanged. Review never blocks the course and keeps working after the course is finished. An item whose question left the content is ignored.

### Kit viewer
`GET /api/kit` reads only files inside the bundled `kit` folder, as text. `ref` must be `kit:` followed by a forward-slash relative path: no empty, `.` or `..` parts, no backslash, drive letter, colon (alternate streams), `~` (8.3 short names), leading slash, trailing dot or space, device names or directory. A file named `answer-key.md` is never readable: the check runs on the requested name and again on the path the file really resolves to on disk (so case and short-name aliases cannot get past it). Every failure is `bad_ref` with a plain message.

### `progress.json` `lessons` block
```
"lessons": {"seed": str|null,
  "per_lesson": {"<id>": {"status": null|"done"|"skipped", "migrated"?: true,
                          "activities": {"<id>": {"passed","attempts","first_try","last"}}}},
  "placement": {"<id>": {"correct":bool,"option":id,"decision":null|"accepted"|"declined"}},
  "records": [...], "review": {"items": {...}},
  "step_checks": {"<step>": {"passed","attempts","first_try","last"}}}
```
It holds only what the participant did, never course answers. `status` is null while a lesson is open.

### Older progress
A `progress.json` written before lessons existed has no `lessons` block and loads without error. Each lesson that comes before the furthest completed step in `COURSE` is recorded as `skipped` with `"migrated": true`, so it does not block anything and schedules no reviews; completed steps are kept. With no step done, nothing is migrated and the course starts at the mission.

A `progress.json` written for the earlier eleven-lesson course (ids `loop`, `generate-why`, `build-why`, `choices`, `verify`, `compare`, `fix-why` and the removed activities) loads without error. On load `state.prune_lessons_block` drops the `per_lesson`, `records` and `review.items` entries that name a lesson id not in `state.COURSE`, and, when anything was dropped, `_migrate_new_lessons` records each new lesson that comes before the furthest completed step as `skipped` with `"migrated": true`. Completed steps and everything else are kept. Example: `generate` done with records for `loop` and `generate-why` loads with `several-runs` skipped and migrated. `<home>\pending-lessons.json` is pruned the same way whenever it is read (`Engine._read_pending`), so a pending `mission` record merges as before. Review items whose question left the content are ignored.

### Reference and glossary
`content/glossary.json` is `{"terms":[{"term","kind","meaning","lesson"}]}` and covers the series glossary plus the words the lessons use (CLI, agent, markdown, proxy). `kind` is required on every term and is `idea` (a general idea that holds whatever tool is used) or `course` (a term for how this course does it); `lessons.validate_glossary` rejects a term whose `kind` is missing or not one of the two (`lessons.GLOSSARY_KINDS`). A term of kind `course` has a meaning that begins "In this course,". `lesson` names one of the lessons (Part 1's terms name `p1-` lessons and Part 2's name `p2-` lessons). An optional `"card": false` keeps a term out of the printable one-page reference (it stays in the in-app glossary); Part 1's and Part 2's terms carry it so the card keeps fitting one page. The in-app glossary panel and the reference card show two groups, "Ideas" then "In this course", with the group labels from `lesson-ui.json` (`reference.glossary_ideas`, `reference.glossary_course`).

`GET /reference-data.json` (static, no token, no answers) serves the glossary and the reference-card wording from `lesson-ui.json` to `web/reference.html`, the printable one-page reference, and to the in-app glossary panel. **Reference card** (`lesson-ui.json` `reference`), in this order: the method in one line (`method_heading`, `method_line`: ask clearly, know what you need, turn it into rules, score the result, improve, keep a record); a section "How this course works" (`loop_heading`, `loop_lines`: this course's chain of work) with "What this course's checker says" (`verdicts_heading`, `verdicts`: PASS, FAIL and NOT CHECKED as the results this course's checker gives; no exit codes); the glossary in the two groups; and "Principles that always hold" (`principles_heading`, `principles`). It must fit one page when printed.

### Engines without a course
`Engine(lessons=None)` (used by the step tests) has no lessons: `course` lists the steps only, `series` is null, steps unlock as before, and every lesson route returns `no_lessons`. The kit viewer works without a course.
